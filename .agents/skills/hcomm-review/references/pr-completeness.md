# 检视规范：PR 描述与测试完备性

对照 PR 描述、关联 Issue 与实现三者一致性核查。

## PR/Issue 与实现吻合度

- 描述声称的每个改动点都能在 diff 中找到对应实现（防"声称了但没做"）
- diff 中的核心变更在描述中有交代（防"做了但没说"，尤其是不在声称范围内的夹带修改）
- 关联 Issue 的诉求逐条被实现覆盖；实现未超出 Issue 范围引入无关变更
- PR 描述按 `.gitcode/PULL_REQUEST_TEMPLATE.zh-CN.md` 填写（描述/变更类型/关联 Issue/测试/文档更新/合入检查）

## 功能正确性

- 对照描述逐条核验实现逻辑是否达成目标；核心逻辑须读完整函数体而非仅 diff
- 修改行为时同步核验调用方是否适配（grep 调用点）

## 测试完备性

- 生产代码变更（`src/`）须有对应 UT/ST 补充；`test/` 无变更时在意见中质询测试覆盖
- UT 断言须校验行为结果而非仅"不崩溃"；新增接口至少覆盖正常路径 + 关键错误路径
- PR 描述「测试」一节须列出已执行用例与结果

## 文档同步

- 接口/行为变更同步 `docs/`（api_ref、架构文档）；新增模块补 architecture-brief 对应小节（如适用）
- 新增/变更软件模块须同步补充、更新该模块的代码级目录文档（口径与产出方式见下节"模块目录文档同步"）
- 对外头变更见 `external-api.md` 的资料同步条目

## 模块目录文档同步

新增/变更模块代码时，核查代码级目录文档是否同步（本文"文档同步"的模块粒度落地）。模块目录文档指归档在模块目录下、按六段骨架（功能/目录/流程/数据/接口/限制）组织的代码级解析文档（如 `src/coll_communicator_mgr/dfx/taskException/taskException.md`），非 docs/ 下的接口参考或指南。

**核查步骤**（对 PR 触碰的每个模块目录执行）：

1. **查现状**：模块目录下是否已存在代码级目录文档（`模块名.md`/`模块名_en.md`，存量 `README.md`/`README_en.md` 也算）。
2. **无文档时**：结合本次改动内容判断是否应补——满足任一条即建议本次补齐（LOW 意见）：
   - 新增独立模块/组件目录（新目录 + 多个源文件）
   - 为既有目录新增核心类/核心流程，模块复杂度显著上升
   - 纯小改动（修 bug、调参数、少量行级变更）不强制，不提意见
3. **有文档时**：判断是否需要更新——判定基准为**六段骨架应覆盖的范围**（应然全集，与 hcomm-doc-dev/software-module 的存量适配口径"触碰更新时按统一骨架走"一致），而非文档实际写了什么：
   - 改动使文档既有陈述失效（接口/流程/类/约束与代码不一致）→ 必须同步更新（MEDIUM 意见）
   - 改动落在六段应覆盖、但文档实际缺失或未覆盖的部分（如改了对外接口签名，而接口描述章节缺失或未列该接口）→ 同样提 MEDIUM 意见：本次触碰更新顺带补齐该部分；存量文档缺整段骨架时，先与作者确认补齐范围再动
   - 不属于六段应覆盖范围的辅助细节变化（不影响文档任何既有陈述）可不更新
4. **产出方式**：补充或更新文档时，使用 `hcomm-doc-dev` skill 的 software-module 子规范（`.agents/skills/hcomm-doc-dev/references/software-module/module-doc.md`）——六段骨架、Mermaid 三图、中英双语成对输出（`模块名.md` + `模块名_en.md`）、三层校验，以其 module-doc.md 与同目录 references 为写作规范。
5. **验收回查**：作者补充/更新文档后（后续 commit），复检时按 hcomm-doc-dev/software-module 的 Step 5 三层校验口径抽查——文档与代码一致性（接口签名/流程分支）、中英对齐、硬件代号合规；不通过则继续提意见。

**意见落点**：在 PR 主入口文件（或模块目录代表文件）的新增/变更行提按行意见，写明"缺文档，建议本次补充"或"文档第 X 节已过期，须同步更新"，并指明可用 hcomm-doc-dev skill 的 software-module 子规范产出。
