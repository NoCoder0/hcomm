
# Software Module Doc（软件模块/组件代码级解析文档写作规范）

## Overview

为代码仓库中的一个模块目录产出**代码级解析文档**：读透目录下全部源文件，按固定六段骨架（功能/目录/流程/数据/接口/限制）成文，**中英双语成对输出为强制要求**。文档面向新接手模块的开发者，做到"不读源码也能理解模块全貌，要改源码时能按图索骥"。

## 适用边界

- 本子规范（software-module）**仅适用于对代码仓的单个模块/组件目录下的代码进行分析并输出文档**：输入是源码目录（如 hcomm 的 dfx/taskException、dfx/profiling），产出是随代码目录归档的代码级解析文档。
- **docs/ 等文档目录下的文档输出不使用本子规范**（如 docs/zh/api_ref/ 接口文档、构建指南、开发指南、教程等），此类文档有其自身规范，与代码级解析文档的六段骨架无关。
- 若目标目录实际包含多个相对独立的组件/模块，先**暂停并向开发者确认**拆分与描述口径是否符合预期（见 Step 2 接口描述优先级），确认后再继续。
- 若目标仓为 hcomm，同时复用仓内已有 skill 资源（见"复用仓内资源"节），避免重复规范。

## 触发场景

- "给 XX 模块目录写个文档 / README / 代码解析"
- "参考 taskException.md 的风格，给 YY 目录出一份文档"
- "把 ZZ 模块文档补上英文版"（存量中文文档补英文版时，骨架规则同样适用；前提是存量文档本身是模块目录下的代码级解析文档）
- 任何"目录粒度 + 代码级深度 + 中英双语"的文档需求

不触发：docs/ 目录下的文档（API 参考、构建/开发指南、教程、RFC 等）——这些不属于代码级模块解析文档，勿套用六段骨架。

## 文档骨架（六段，顺序固定，原则上不可裁剪）

```markdown
# <模块名> 模块代码解析          ← H1，与目录名一致

## 功能描述                      ← 定位一句话 + 分侧职责 + 使用场景 + 与周边模块的关系 + 核心能力编号列表
## 目录描述                      ← 目录树 + 文件间关系表 + 组件交互图
## 流程描述                      ← 每个核心流程一张时序图（覆盖全部核心流程）
## 数据描述                      ← 类图（覆盖全部核心类）
## 接口描述                      ← 对外接口总表（索引）+ 按类完整表（详写）

## 使用限制                      ← 支持的场景表 + 规格约束编号列表（+已知限制）
```

- 六段全部保留，不因模块小而裁剪；内容多少随模块规模伸缩，但章节结构与顺序不变。**章节名统一用裸标题，不加括号后缀**（不写"流程描述（Mermaid时序图）""数据描述（类图）"等，图表类型由每段规范约定）。
- **命名规则（单一流派）**：`模块名.md` / `模块名_en.md`（如 taskException.md / taskException_en.md），模块名与目录名一致（hcomm 仓基线见 FN-04）。
- 存量目录中以 `README.md` / `README_en.md` 命名的（如 cluster_monitor/、rtsq_poll/），触碰更新时**建议改名为 `模块名.md` / `模块名_en.md`**（需用户确认后随本次更新一并完成，改名后原文件删除不留副本）。
- **英文版是强制交付物**：任何时候产出中文版，必须同步产出对应的 `_en.md`，缺一不可。

## 图表工具选型（同类图/表统一用一种工具）

| 图/表类型 | 工具 | 备注 |
|----------|------|------|
| 组件交互图 | Mermaid `graph TB` | 目录描述章节 |
| 流程/时序图 | Mermaid `sequenceDiagram` | 流程描述章节，一流程一张 |
| 类图 | Mermaid `classDiagram` | 数据描述章节 |
| 目录树 | ```text 代码块 | 目录描述章节 |

同类图/表禁止混用多种工具（如同一文档内时序图不许一张用 Mermaid、一张用 ASCII）。

## Workflow（写作流程）

### Step 1. 探查阶段 —— 读透目录

1. 列出目标目录全部文件（含子目录 host/、aicpu/ 等），读每个 .h/.cc 的类声明与方法签名。
2. 顺藤摸瓜读外部依赖的头文件（只读被引用的接口与数据结构，不展开整个依赖模块）。
3. 识别模块的"侧别"结构：Host 侧 / Device 侧（按实际执行单元写实名：AICPU、CCU、MC2 等）/ 双侧共用，这是功能描述与目录描述的分线依据。
4. 找出三样东西：**对外功能接口**（判定标准为**调用边界而非语言可见性**——模块目录之外有调用的接口即为对外，含经回调注册被外部触发；grep 调用点核实，不凭 public/private 推断）、关键数据结构、跨模块交互点。
5. hcomm 仓：模块定位（属于哪个子系统、哪一层）以仓根 `AGENTS.md` 与 `docs/zh/architecture/architecture-brief.md` 为权威参考，不凭印象写。

### Step 2. 结构阶段 —— 定内容清单（全量覆盖原则）

按骨架六段逐段列出"这一段要写什么"，条目来自 Step 1 的探查结果：

- **功能描述**：模块定位（属于什么体系、哪一层）、分侧职责、**使用场景**（什么情况下会用到该模块、由谁在什么流程中触发）、**与周边模块的关系**（依赖哪些模块获取什么、被哪些模块调用、通过什么接口/机制交互——概览级，文件级细节归目录描述章节）、核心能力列表（动词开头、每条可对应到具体接口）。
- **目录描述**：目录树（每个文件一行注释）、文件间关系表、组件交互图节点与边。
- **流程描述**：**覆盖全部核心流程**，不是挑几个——初始化/注册、主处理（按模式分子流程）、异常/退出路径，**以及与周边模块/组件的交互流程（回调注册、事件通知、数据上报等）**，一个不落。每个核心流程一张时序图，跨模块消息涉及的周边类/回调画进图。
- **数据描述**：以类图承载（Mermaid classDiagram），**覆盖全部核心类**，含成员变量、方法签名、静态/依赖关系；数据结构类（错误信息结构、上下文结构）一并入图；外部组件类画为依赖终点，关系线标注用途与交互机制（调用/回调/通知），依赖与被调用方向都要表达。
- **接口描述**：**对外接口总表（索引）在前、按类完整表（详写）在后**：
  1. **对外接口总表**：模块对周边提供的所有功能接口一表列全（extern "C" 入口、被模块外调用的公有方法、注册给外部的回调、跨模块全局函数）——判定标准为调用边界（模块外有调用即对外），非 public/private；总表只做一句话索引，详细描述一律在类表。
  2. **按类完整表**：每个核心类一张五列表，类的全部核心接口都在（含对外方法——核心类横跨模块内外是常态，对外公有方法在"类型"列标"公有（对外）"）；模块内接口按详略分级——主流程必经方法详写，辅助方法（getter/setter、纯工具函数）从略或合并（注明判断依据）。
  3. **多组件目录先确认**：若探查发现目录含多个相对独立的组件/模块，**暂停**，向开发者说明发现的组件划分，确认"按核心组件展开还是拆成多份文档"后再继续。
- **使用限制**：场景表 + 规格约束列表（+已知限制）。

### Step 3. 写作阶段 —— 分段成文

按骨架顺序写，各段的详细写作规范见 `references/writing-rules.md`，Mermaid 图规范见 `references/mermaid-guide.md`。要点：

- **信息可佐证（红线）**：输出的所有文档内容必须确保有代码或其他可靠资料能够佐证——每条事实性陈述（接口行为、流程分支、常量值、约束规格、模块定位等）都应能回溯到源码、头文件或仓内权威文档（AGENTS.md、architecture-brief.md 等）。文档中不展示证据本身，但来源必须真实可靠。**禁止将猜测、推断或编造的内容写进文档**；源码读不透、行为不确定时，回到代码确认，确认不了的内容不写。

- 先写中文版全文，再产英文版（Step 4，强制）。
- **存量文档更新时，正文旧硬件代号一并替换**：被更新文档正文中已存在的内部硬件代号（CKE、Xn、GSA、MS），在本次更新涉及的章节内替换为 C++ API 类名（Event、Variable、Address、CcuBuffer），映射与例外见 `references/terminology.md` 的"hcomm 硬件代号规避"节；未触碰的章节不主动改写（避免大范围 diff 淹没本次更新内容）。
- **通用 Markdown 写作规范直接加载仓内已有 skill 文档**：`<仓根>/.agents/skills/hcomm-review/references/markdown-writing.md`（文件命名/标题/列表/表格/标点/链接/注释符号/敏感词等 14 类规则），本文与 references 不复制其内容、与其冲突时以仓内规范为准。目标仓没有该文件时，按本子规范 writing-rules.md（与本文件同目录）中的最小基线执行。
- 每张图、每张表写完立即自查：图里的每个节点/箭头是否都对应真实类名/函数名？表里的每个参数名是否与源码一致？
- 行号引用格式：``源码：`file.cc:123-145```。行号须实证取得（grep -n），禁止估算；行号漂移风险高的位置改用常量名/函数名锚定。

### Step 4. 中英双语对齐（强制）

- 英文版与中文版**逐节语义对齐**，非逐句直译。骨架标题对应关系见 `references/terminology.md`。
- 代码符号（类名/函数名/常量名/错误码/十六进制值）原样保留，不翻译。
- 表格、目录树、Mermaid 图代码块中原样复用（只译 subgraph 名、Note、边标签等自然语言部分），避免两版图结构漂移。
- 术语表、翻译句式、hcomm 硬件代号规避规则见 `references/terminology.md`。

### Step 5. 校验阶段 —— 三层核对

**先跑确定性脚本**（写完/改完文档即跑，ERROR 清零才算过）：

```bash
python3 .agents/skills/hcomm-doc-dev/scripts/software-module/doc_lint.py <模块名>.md --en <模块名>_en.md --repo-root <仓根> --head-sha <head_sha>
```

四项确定性检查由脚本完成：硬件代号扫描、中英结构对齐（标题/表格/图/代码块数量）、行号引用实证（裸文件名自动唯一定位）、Mermaid 易错点（`~` 转义/`end` 歧义/中文括号/节点 ID 中文标点）。脚本覆盖不到的**语义级核对**（行为一致性、符号真实性、佐证链）仍按下述三层逐条执行；无 Python 环境时按各条目手动方式兜底。

**第一层：中文文档与代码实现一致性（二次确认，必做）**

1. 接口表核对：每个对外接口的函数名、参数列表（类型、顺序、个数）、返回值类型与头文件**完全一致**；参数逐个有解释、输入/输出标注正确——核对方法沿用仓内 `.agents/skills/hcomm-review/references/markdown-api-accuracy.md` 的 PH/PA 规则。
2. 流程/行为核对：文档描述的流程分支、触发条件、常量值（如 `TASK_CONTEXT_SIZE = 50`）逐条回到源码确认，描述的语义与代码实现一致（不止符号存在，行为也要对）。
3. 图核对：图中类名/函数名与源码一致（每张图抽查 ≥3 个符号），交互关系（谁调谁）与调用点吻合。
4. 行号引用实证：所有 `file.cc:行号` 引用用 grep -n 复核，与实际行号一致（doc_lint.py 已含格式与存在性检查，此步复核内容语义仍属人工）。
5. Mermaid 语法可渲染（重点检查 `~` 泛型转义、`end` 关键字冲突、节点名含特殊字符——doc_lint.py 已覆盖常见易错点，此步为渲染级复查）。

**第二层：中英一致性**

6. 两版章节结构一致（标题层级、表格数量、图数量、图结构）。
7. 代码符号、常量值、错误码值在两版中逐一对应。

**第三层：合规检查**

8. 硬件代号扫描：本次产出/更新的正文中不出现 CKE、Xn、GSA、MS（grep 复核；代码块与反引号内的源码标识符除外），出现即按映射表替换。
9. 佐证复核：抽查文档中的事实性陈述（接口行为、流程分支、常量值、约束规格），逐条确认能回溯到源码或权威资料；回溯不到的内容删除或修正，不允许"看着像对的"就放过。

问题项回到对应章节修正后重查，不允许"记录待办"式跳过。
