## Description

Starts a software conditional branch block within a CCU kernel. The condition is computed by the CCU hardware at runtime. If the condition is not met, execution jumps to the `CCU_ELSE` branch or to the exit of the if block.

`CCU_IF` is a preprocessor macro. It can be used alone or followed by an optional `CCU_ELSE` branch. `CCU_IF` and `CCU_ELSE` are automatically paired through internal state management of the macros, so you only need to write them according to the macro syntax.

## Macro Syntax

```cpp
CCU_IF(condExpr) {
    // Body of the then branch.
}

// Optional: followed by CCU_ELSE.
CCU_IF(condExpr) {
    // Body of the then branch.
} CCU_ELSE {
    // Body of the else branch.
}
```

## Parameters

| Parameter | Description |
| --- | --- |
| condExpr | Conditional expression of the `AscendC::ccu::CondExpr` type. It is generated by `operator==(uint64_t)` or `operator!=(uint64_t)` of `ccu::Variable`, for example, `v == 0` or `v != limit`. The condition is computed by the CCU hardware at runtime. |

## Return Value

`CCU_IF` is a preprocessor macro and does not return [CcuResult](../../../datatype_definition/CcuResult.md) by itself. After macro expansion, if an internal error occurs (such as a duplicate label or an invalid handle), `CCU_E_PARA`/`CCU_E_NOT_FOUND` may be generated. In this case, the macro does not throw an exception or block registration: on failure, the body is skipped, but registration still succeeds. This is the same type of situation as "the body is skipped when `CCU_ELSE` cannot be paired" - the error is not fed back through the return value, so pay attention to it during debugging.

## Constraints

- `CCU_IF(condExpr)` must be followed by a then code block enclosed in {}.
- For Ascend 950PR&950DT products, the current `condExpr` of `CCU_IF` supports only the == and != comparison modes.
- `CCU_IF` can be used alone (without `CCU_ELSE`) or together with `CCU_ELSE`. Both usages are valid.
- Nesting is supported: `CCU_IF` can be nested inside another `CCU_IF`.
- `CCU_IF` is not recommended for use inside the body lambda of a hardware loop (`ccu::Loop`) -- software branching is not supported inside a hardware loop body. The framework does not forcibly verify it, but the behavior is undefined.
- The immediate value (`imm`) compared in `condExpr` must be of the `uint64_t` type. Comparison between two variables is not supported for direct use in `CCU_IF`.

### Why No Other Calls Can Be Inserted Between `CCU_IF` and `CCU_ELSE`

The closing of `CCU_IF` does not occur immediately at the closing brace of `CCU_IF { body }`; instead, it is deferred to one of the following three occasions:

1. The immediately following `CCU_ELSE`;
2. The first CCU API call after it;
3. The fallback closure at the end of `HcommCcuKernelRegister`.

> Side effect: If any CCU API call is inserted after `CCU_IF { body }` and before `CCU_ELSE`, `CCU_IF` is closed prematurely. The subsequent `CCU_ELSE` then cannot find a matching `CCU_IF`, and its body is skipped (registration still succeeds without reporting an error). Therefore, ensure that no other CCU API call exists between the two. For details, see the constraints in [CCU_ELSE](CCU_ELSE.md).

## Example

```cpp
using namespace AscendC::ccu;

// Scenario: Select different data movement paths based on the runtime variable value.
CcuResult MyKernel(CcuKernelArg arg) {
    Variable flag;
    LoadArg(flag, 0);   // Load the runtime flag from taskArgs[0].

    CCU_IF(flag == 0) {
        // Execute this branch when flag is 0.
        Variable a, b;
        a = 10;
        b = 20;
    } CCU_ELSE {
        // Execute this branch when flag is not 0.
        Variable c;
        c = 99;
    }

    return CCU_SUCCESS;
}
```
